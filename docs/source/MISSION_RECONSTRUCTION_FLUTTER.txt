# MISSION — RECONSTRUCTION COMPLÈTE D’ELECTROSIM EN FLUTTER/DART

Tu disposes de deux sources principales :

1. `Cahier_des_charges_ElectroSim_Flutter_Nouveau_Noyau.pdf`
2. Le dernier ZIP disponible de l’application ElectroSim historique.

Ta mission consiste à **reconstruire ElectroSim proprement en Flutter/Dart selon le cahier des charges**, en travaillant de manière autonome, progressive, contrôlée et vérifiable.

## 1. HIÉRARCHIE DES SOURCES

Le cahier des charges Flutter constitue la **source de vérité architecturale et fonctionnelle principale**.

L’ancien ZIP ElectroSim constitue uniquement :

- une référence fonctionnelle ;
- une référence ergonomique ;
- une référence visuelle ;
- une source permettant de comprendre les fonctionnalités existantes ;
- une source permettant d’identifier les composants et comportements utiles ;
- un oracle de comparaison lorsque le cahier des charges demande de conserver un comportement.

Il ne constitue PAS l’architecture du nouveau projet.

### Interdictions

Ne pas :

- convertir automatiquement l’application TypeScript en Dart ;
- reproduire son architecture historique ;
- recopier ses dépendances globales ;
- reproduire les anciennes incohérences ;
- conserver les anciens mécanismes de FaultEngine par injection ;
- importer automatiquement les anciens schémas ;
- importer automatiquement les anciennes pannes ;
- créer des dépendances entre exemples de câblage et scénarios de panne ;
- conserver du code uniquement parce qu’il existait dans l’ancienne version.

Le nouveau projet doit repartir sur une architecture propre.

---

# 2. OBJECTIF FONDAMENTAL

Construire une nouvelle génération d’ElectroSim basée sur :

**Flutter + Dart + nouveau moteur électrique déterministe.**

Architecture centrale obligatoire :

`CircuitState`
→ `TopologyEngine`
→ `SolverEngine`
→ `SimulationResult`

`CircuitState` doit être la seule source de vérité électrique.

Aucun écran, widget, Canvas, TP, module énergie, multimètre, scénario de panne ou système EIE ne doit disposer d’une représentation concurrente de l’état électrique.

---

# 3. SÉPARATION ABSOLUE EXEMPLES / PANNES

Cette règle est non négociable.

## Exemples

Les exemples sont exclusivement des :

**circuits correctement câblés, fonctionnels et pédagogiquement validés.**

Ils servent :

- à observer un montage ;
- à comprendre un câblage ;
- à démarrer un exercice ;
- à présenter un exemple de fonctionnement normal.

## Scénarios de panne

Une panne est un **circuit autonome déjà défectueux**.

Elle peut contenir directement :

- mauvais branchement ;
- conducteur manquant ;
- conducteur mal connecté ;
- court-circuit ;
- inversion de conducteurs ;
- inversion de polarité ;
- perte de phase ;
- mauvaise séquence de phases ;
- composant défectueux ;
- contact bloqué ;
- bobine coupée ;
- lampe grillée ;
- moteur défaillant ;
- appareil hors service ;
- mauvais réglage ;
- alimentation anormale ;
- combinaison de plusieurs défauts.

Les scénarios de panne ne sont PAS obtenus en prenant un exemple et en injectant une panne.

Architecture interdite :

`ExampleCircuit + FaultInjection`

Architecture obligatoire :

`FaultScenario → FaultyCircuitState`

Il ne doit exister aucune dépendance fonctionnelle entre bibliothèque d’exemples et bibliothèque de pannes.

Le nouveau projet commence avec :

- 0 ancien exemple importé ;
- 0 ancienne panne importée.

Les bibliothèques seront reconstruites ultérieurement uniquement à partir de contenus validés.

# 4. NOUVEAU MOTEUR ÉLECTRIQUE

Le Canvas Flutter ne calcule jamais l’électricité.

Il représente uniquement le résultat du moteur.

Flux obligatoire :

`CircuitState`
→ compilation topologique
→ modèle électrique
→ solveur
→ états physiques
→ mesures
→ diagnostic
→ rendu graphique

## CC

Construire un véritable solveur fondé sur l’analyse nodale modifiée, ou une méthode mathématique équivalente suffisamment générale.

Il doit traiter proprement :

- tension ;
- courant ;
- résistance ;
- sources ;
- branches ;
- série ;
- parallèle ;
- nœuds ;
- circuits ouverts ;
- courts-circuits ;
- composants commutables ;
- mesures ;
- plusieurs sources lorsque le modèle le permet.

## AC monophasé

Utiliser les grandeurs complexes.

Prendre en charge au minimum :

- impédance ;
- résistance ;
- réactance ;
- tension complexe ;
- courant complexe ;
- déphasage ;
- puissance active P ;
- puissance réactive Q ;
- puissance apparente S ;
- cos φ.

## AC triphasé

L1, L2, L3 et N doivent être explicitement représentés.

Ne pas modéliser le triphasé comme « une phase × 3 ».

Prévoir notamment :

- réseau équilibré ;
- réseau déséquilibré ;
- neutre ;
- perte de phase ;
- inversion de phases ;
- ordre des phases ;
- charges triphasées ;
- charges monophasées raccordées au réseau triphasé.

## PV

Créer un domaine PV propre et testable conformément au cahier des charges.

# 5. MODÈLES DES COMPOSANTS

Chaque composant doit posséder un modèle métier explicite.

Exemple de structure conceptuelle :

`ElectricalComponent`

avec :

- identifiant unique ;
- type ;
- bornes ;
- paramètres nominaux ;
- modèle électrique ;
- état physique ;
- limites ;
- propriétés ;
- métadonnées nécessaires.

L’état visuel ne doit jamais remplacer l’état physique.

Exemple :

Le ventilateur ne tourne pas parce que l’animation est activée.

Il tourne parce que :

`SolverEngine → DeviceStateEngine → running`

et Flutter représente ensuite cet état.

# 6. MOTEUR TOPOLOGIQUE

Créer un `TopologyEngine` indépendant du moteur graphique.

Il doit construire et analyser :

- bornes ;
- connexions ;
- conducteurs ;
- nœuds ;
- branches ;
- composants connectés ;
- chemins électriques ;
- éléments isolés.

Il doit pouvoir détecter avant résolution :

- borne flottante ;
- absence de retour ;
- circuit ouvert ;
- court-circuit topologique ;
- composant isolé ;
- connexion impossible ;
- conducteur manquant ;
- source incohérente ;
- problème de phase ;
- incohérence structurelle.

# 11. DIAGNOSTIC ET EIE

L’EIE doit devenir un moteur fondé sur des preuves.

Flux attendu :

`TopologyEngine`
+
`SolverEngine`
+
`MeasurementEngine`
+
états des composants
→
`DiagnosticEngine`
→
EIE

L’EIE ne doit jamais inventer une cause.

Elle doit pouvoir distinguer :

- observation ;
- anomalie mesurée ;
- hypothèse ;
- cause confirmée.

Lorsque cela est possible, une recommandation EIE doit pouvoir localiser graphiquement l’élément concerné.

---

# 12. TP DE CÂBLAGE

Le TP de câblage doit s’appuyer sur des circuits fonctionnels.

Le système doit permettre :

- consigne ;
- circuit attendu ;
- progression ;
- mesures ;
- vérification ;
- validation ;
- évaluation.

Une validation doit provenir de l’état réel du circuit, et non d’un simple indicateur UI.

---

# 13. RECHERCHE DE DÉRANGEMENT

Un TP de recherche de dérangement charge directement un `FaultScenario`.

L’élève reçoit :

- le circuit défectueux ;
- les consignes ;
- les outils de mesure nécessaires.

Il ne doit jamais recevoir les données privées expliquant la panne.

Prévoir une structure privée professeur de type :

`teacherTruth`

comprenant :

- défaut réel ;
- symptômes attendus ;
- mesures attendues ;
- méthode de vérification ;
- critères de réparation ;
- critères d’évaluation.

La validation de la réparation doit être physique :

circuit réparé
→ recalcul complet
→ contrôle topologique
→ contrôle électrique
→ contrôle fonctionnel.

Ne jamais valider uniquement parce qu’un identifiant de panne a disparu.

# 15. QUALITY GATES OBLIGATOIRES

À la fin de chaque phase, exécuter tous les contrôles pertinents.

Minimum attendu :

### Analyse statique

- `flutter analyze`
- absence d’erreur Dart ;
- absence d’avertissements critiques ;
- règles de lint respectées.

### Tests unitaires

Tester chaque classe métier importante.

### Tests d’intégration

Tester les interactions entre modules.

### Tests widget

Tester les éléments Flutter.

### Tests golden

Utiliser des tests visuels lorsque pertinents.

### Tests électriques

Créer des circuits canoniques dont les résultats sont mathématiquement connus.

### Tests topologiques

Tester les anomalies structurelles.

### Tests de persistance

Tester :

enregistrement
→ fermeture
→ ouverture
→ comparaison exacte.

### Tests de déterminisme

La même entrée doit toujours produire le même résultat dans les mêmes conditions.

### Tests de performance

Surveiller :

- temps de résolution ;
- fluidité ;
- consommation mémoire ;
- rendu graphique.

### Tests responsive

Tester au minimum :

- petit écran ;
- tablette ;
- desktop.

---

# 16. RÈGLE DE BLOCAGE

NE PAS passer à la phase suivante lorsqu’un test requis échoue.

Si une anomalie apparaît :

1. reproduire ;
2. isoler ;
3. identifier la cause racine ;
4. corriger ;
5. créer un test empêchant sa réapparition ;
6. rejouer l’ensemble des tests concernés ;
7. seulement ensuite poursuivre.

Ne pas masquer un problème par un contournement visuel.

---

# 17. RÉGRESSION

Chaque correction de bug doit ajouter un test de non-régression.

Une anomalie corrigée ne doit jamais pouvoir revenir silencieusement.

Conserver une suite cumulative de tests.
